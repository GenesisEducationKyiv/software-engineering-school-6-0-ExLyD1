# Message Broker (RabbitMQ)

Як у цьому застосунку відправляється пошта — і що ще варто доробити.

## Потік

API **ніколи не шле лист сам.** Він кладе **команду** `SendEmail` у чергу RabbitMQ,
а окремий `notification-service` забирає її та шле через Resend.

```
API (publisher) → [RabbitMQ: email_commands] → notification-service → Resend
```

## Що брокер робить для нас (4 властивості)

- **Routing (маршрутизація)** — producer кладе не «в чергу», а в *exchange*, який за
  правилами розкладає по чергах. У нас — default exchange, routing key = імʼя черги
  (`email_commands`), тобто пряма доставка в одну чергу.
- **Buffering (буфер)** — якщо consumer лежить, повідомлення **чекають** у черзі.
  (Перевірено: вимкнули сервіс → 3 листи чекали → увімкнули → доставив усі.)
- **Ack (підтвердження)** — consumer підтверджує обробку (`ack`). Непідтверджене при
  падінні consumer'а брокер **передоставляє** (звідси можливі дублі — див. нижче).
- **Consistency (гарантії)** — durable-черга + persistent-повідомлення + data-volume →
  переживають рестарт брокера. Модель доставки — **at-least-once**.

## Коли доставка падає — DLQ

Consumer робить `nack(requeue=false)` → завдяки `x-dead-letter-exchange` повідомлення
потрапляє в **`email_commands.dlq`**.

Чому не `requeue=true`: «отруйне» повідомлення (яке завжди падає) зациклилося б —
впав → у чергу → знову впав. DLQ розриває цей компроміс: листи **не губляться**
(на відміну від простого відкидання) і **не зациклюються** — їх можна переглянути
чи перевідправити вручну.

## Відомо й варто доробити (next steps)

- **Дублі / ідемпотентність.** at-least-once означає, що той самий лист може прийти
  двічі (consumer надіслав, але впав до `ack`). Лікується унікальним `id` повідомлення +
  дедуплікацією. Наш consumer навмисно **без БД** (stateless) — тож це trade-off,
  не безкоштовно.
- **Авто-ретрай перед DLQ.** Зараз невдале повідомлення йде в DLQ одразу — тимчасові
  збої не перевідправляються. Наступний крок: retry-черга з TTL + лічильник спроб +
  jitter, і лише після N невдач → DLQ.
- **Dual-write.** Підписка робить `COMMIT` у БД, потім публікує. Якщо публікація впаде
  між цими кроками — підписка є, листа нема. Правильно — transactional outbox.
