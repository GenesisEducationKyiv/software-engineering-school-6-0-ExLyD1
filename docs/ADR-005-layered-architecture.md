# ADR-005: Шаруватий модульний моноліт + тести архітектурних залежностей

---

## Статус

**Статус:** Accepted
**Дата:** 2026-07-06
**Автор:** Яхній Олександр

---

## Контекст

Моноліт розрісся до кількох доменних модулів (`subscriptions`, `scanner`, `saga`) плюс
інфраструктура (`shared`). Межі між ними трималися лише на дисципліні — нічим не
перевірялися. Наслідок: між `subscriptions` і `saga` виник **реальний цикл**:

- `subscriptions/controller` → `saga/orchestrator` (щоб стартувати сагу);
- `saga/orchestrator` → `subscriptions/repository` (щоб створити pending-підписку й
  компенсувати).

Завдання ДЗ: **описати архітектуру в docs** і (зірочка) **зробити розподіл шарів +
тести архітектурних залежностей**, які не дадуть таким зв'язкам повернутися.

---

## Рішення

**Шаруватий модульний моноліт** із чотирма шарами й одностороннім правилом залежностей.

### Шари

| Шар | Файли | Роль |
| --- | --- | --- |
| Controller | `*.controller.ts` | HTTP: валідація, статус-коди, маппінг помилок |
| Service | `*.service.ts` | бізнес-логіка в межах модуля |
| Repository | `*.repository.ts` | єдиний, хто пише SQL / доступ до БД |
| Shared | `modules/shared/**` | інфраструктура (db, messaging, github, mailer…) |

### Правило залежностей

1. Залежності вказують **в один бік**: `controller → service → repository → shared`.
2. `shared` **ніколи** не залежить від доменних модулів.
3. Модуль звертається до іншого модуля **лише через його `index.ts`** (публічний
   API-барель), а не в його внутрішні файли.
4. Циклів немає.

### Публічний API через `index.ts` (барелі)

У кожного доменного модуля з'явився `index.ts`, який реекспортує лише те, що є
публічним контрактом:

- `saga/index.ts` → `startRegisterSubscription`, `startRelay`, `startReplyConsumer`, типи-порти;
- `subscriptions/index.ts` → `subscriptionRoutes`, `notifyRelease`, `deleteByConfirmToken`;
- `scanner/index.ts` → `startScanner`.

Внутрішні файли (`*.repository.ts`, `*.orchestrator.ts` тощо) — приватні.

### Розрив циклу через інверсію залежностей

`saga` більше **не імпортує** `subscriptions`. Замість цього оркестратор приймає дві
функції-порти, які інжектить композиційний корінь `app.ts`:

- `CreatePendingSubscriptionFn` — створити pending-підписку в транзакції саги;
- `CompensateFn` — компенсація (видалення).

Тепер стрілка йде тільки `subscriptions → saga`; назад — нічого. Це класична
**Dependency Inversion**: обидва модулі залежать від абстракції (тип функції), а
конкретну реалізацію зшиває корінь.

## Enforcement — dependency-cruiser (fitness-функції)

Правила закодовані в `.dependency-cruiser.js` і запускаються `npm run arch`. Порушення
= `error` = червона збірка. Це і є «тести архітектурних залежностей».

| Правило | Що ловить |
| --- | --- |
| `no-circular` | будь-які цикли (щоб розірваний `subscriptions↔saga` не повернувся) |
| `shared-not-to-modules` | інфраструктура не тягне домен |
| `repository-not-upward` | репозиторій не знає про service/controller |
| `controller-not-to-repository` | контролер іде через service, не напряму в репозиторій |
| `cross-module-only-via-index` | модулі бачать одне одного лише через `index.ts` |

`app.ts` (композиційний корінь) виведений з-під правила #5 **за конструкцією** — він
лежить поза `src/modules`, тож правило на нього просто не матчиться. Тестові файли
(`_tests`) виключені, бо мокають внутрішні модулі напряму.

### Чому dependency-cruiser, а не альтернативи
- декларативні правила на регексах шляхів + **backreference груп** (`$1`) для умови
  «інший модуль» — саме це дає правило #5;
- рідний TS-resolver (розуміє наші `.ts`-імпорти й `tsConfig`);
- один devDep + npm-скрипт, без важкого монорепо-тулінга (nx/turbo).

### Чому конфіг `.js`, а не `.ts`
Конфіг тулінга — не application source: він поза `src`, `tsc` його не компілює, у прод
не їде. depcruise **не підтримує `.ts`-конфіг нативно** (парсить невідоме розширення
як JSON5 → падає). Тож обрано **ESM `.js` з `export default`** — той самий стиль, що
`eslint.config.js`, а типізацію дає JSDoc `@type` (TS-інтелісенс без TS-синтаксису).

## Відома межа: «БД ніколи напряму» — конвенція, не enforced-правило

Була ідея заборонити доступ до БД повз шар репозиторію. Це правильний намір
(persistence ignorance), але **dependency-cruiser його перевірити не може**, і це
важливо розуміти:

- depcruise бачить **граф імпортів між модулями**, а не виклики методів усередині файлу;
- runtime-хендл БД приходить не через `import`, а через Fastify-декоратор `fastify.pg`;
- отже `fastify.pg.query('SELECT 1')` — це call-expression, **невидимий** для графа
  залежностей (приклад: [health.controller.ts](../src/modules/shared/health/health.controller.ts) робить `SELECT 1` напряму).

Це урок про **роздільну здатність fitness-функцій**: межі модулів — рівень
dependency-cruiser; «хто виконує SQL» — рівень виразів, тобто зона eslint
(`no-restricted-syntax`). Свідомо лишаємо це **конвенцією** (не вводимо eslint-правило
й не виносимо транзакцію в `withTransaction`), щоб не роздувати обсяг. Якщо колись
знадобиться жорстке enforcement — шлях відомий: eslint-бан `.query(` поза
`*.repository.ts` + Unit-of-Work хелпер для транзакційного контролю саги.

## Наслідки

### Позитивні
- Цикл розірвано й **захищено від рецидиву** автоматичною перевіркою.
- Межі модулів явні (публічний `index.ts`) — рефактор внутрішнього коду не зачіпає сусідів.
- Архітектурні правила — виконуваний артефакт (`npm run arch`), а не текст у вікі.

### Негативні / trade-offs
- Ще один крок у CI й один devDep.
- Барелі додають рівень непрямоти (перехід «до визначення» через `index.ts`).
- Частину бажаних правил (доступ до БД) інструмент не покриває — лишилась конвенцією.

### Відомі обмеження (next steps)
- Додати `npm run arch` у CI-пайплайн поряд із `lint`/`test`.
- За потреби — eslint-правило на «жодного `.query` поза репозиторієм» + `withTransaction`.
- Згенерувати візуальний граф залежностей (`depcruise --output-type dot`) у docs.
